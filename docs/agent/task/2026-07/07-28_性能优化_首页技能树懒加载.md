## 4. 问题与方案

### 4.1 性能根因(全量加载分析)
后端 `ListTree`(`api-server/internal/skillstore/store.go:1183`)递归串行扫描:
1. `os.ReadDir` 同步扫根目录
2. 每个叶子节点串行 `loadFromDir` —— 读 SKILL.md + `utf8.Valid` 校验 + `ParseSkillMD` + `walkFiles` + `listEmptyDirs`
3. 每个叶子 `resolveGlobalSourcePath` —— `os.UserHomeDir` + `EvalSymlinks` + `os.Stat` 探 `~/.agents/skills/`
4. controller 侧 `enrichTreeAppliedTools` 又对每个叶子调 `GlobalAppliedTools` —— 遍历所有 adapter + 多次 `os.Stat`

所有 IO 都是**纯读、无共享状态**,**可安全并发**。前端拿一次 JSON 的代价 = 后端 N 个 skill 的串行 IO 累计。

### 4.2 并发改造方案
**核心思路:两阶段 + errgroup.SetLimit(32) + 宽容错误收集。**

```
ListTree 改造为:
  阶段1(同步,只 ReadDir 不 IO):walk 整棵目录,产出 flat leaf 列表
    [{absDir, name, groupPath, depth}, ...]
    + 收集所有 group 中间层(用于最终构造嵌套 tree)
  阶段2(并发,errgroup.SetLimit(32)):对每个 leaf 并发跑
    loadFromDir + resolveGlobalSourcePath
    失败 → logger.Warn + 跳过(与现有"返回 nil"行为一致)
  阶段3(同步,纯 CPU):按 groupPath 索引,把 leaf 元数据挂回 group 树
    沿用 sortTreeNodes 输出排序
```

**关键设计选择:**
- **group 中间层不并发**:`os.ReadDir` 在 SSD 上 < 0.1ms,串行遍历 100 个目录也只 10ms,不是瓶颈
- **leaf 并发是真正收益点**:每个 leaf 的 `loadFromDir`(读 SKILL.md + 解析)实测 1-3ms,100 个串行 = 100-300ms → 32 并发 = 3-10ms
- **32 worker 选自 SSD 饱和点**:macOS 默认 256 fd soft limit,32 远低于此;100/1000 skill 都够用;不引入配置复杂度
- **宽容错误**:errgroup 不返错,失败的 leaf 走 `logger.Warn` 后跳过(与原 `buildTreeNode` 返回 nil 等价),不阻断整棵树加载
- **不改任何前端代码**:`tree` 响应 JSON 形态完全不变(嵌套 TreeNode 数组),controller / 前端 store / 组件 0 改动

### 4.3 API 兼容性
- `GET /api/skillbox/skills` 响应字段:`items` / `total` / `page` / `size` / `tree` — 全部不变
- `tree` 节点的 `name` / `path` / `is_group` / `children` / `skill_meta` 字段不变
- `skill_meta` 的 `name` / `version` / `description` / `triggers` / `updated_at` / `applied_tools` / `source_path` 字段不变

## 6. 总结
- 完成了什么:`skillstore.ListTree` 从串行递归改为两阶段并发(32 worker),前端 / controller / API 0 改动。
- 留下了什么:并发改造 + 3 个新单测 + 性能基准数据(100/1000 skill)
- 留给下次的事:未来如果业务规模上 10000+ skill,再考虑"懒加载 / 分页"二级方案(本次单层并发已足够)

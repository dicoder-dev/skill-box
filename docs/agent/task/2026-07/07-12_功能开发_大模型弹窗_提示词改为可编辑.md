## 4. 问题与方案

### 4.1 协议走 messages 还是 preset

**Why 改了:** 之前 preset 路线下,前端 raw prompt 只作"显示",真正 system 由后端
`translate_skill` preset 控制 — 这样模板安全和漂移可控,但用户根本改不到 LLM
看到的实际指令,与"可编辑"诉求矛盾。

**新协议:** 走 `chatStream({ messages: [...] })`,system message 直接塞用户编辑后的内容;
preset 留给其它用 preset 的 action 用(不影响)。后端 `chat_stream.a.go` 已经接受 `messages`
入参,不需要改后端。

### 4.2 customPrompt 初始值闪烁

**Why:** setup 阶段 ref('') 默认空,然后等 `watch(open, ...)` 弹窗打开时再 `initPromptOnOpen`
填充 — 用户如果看到 textarea 1 帧空白会不安。

**方案:** 直接 `ref(buildDefaultPrompt(targetLang.value))`,setup 同步阶段就填好。

### 4.3 占位符替换时机

**Why:** 用户在 textarea 里编辑时看到的是 `{target_lang}` / `{skill_md}` 字面量,
这些占位符要保留(可读性)。但 LLM 不能识别大括号语法,需要客户端在**真正发请求**
前完成替换:在 `startTranslate()` 里 `replace(/\{target_lang\}/g, ...)` /
`replace(/\{skill_md\}/g, ...)`。

注:有人会问如果用户手动改坏了占位符(比如 `{target_langs}` 或 `target_lang` 漏大括号)
会怎样? — 用户既然手动编辑了就承担这个后果,而我们的 template 设计明确且不易拼错,
加上占位符都是字面大括号,主观猜测 95%+ 场景能正常替换。

### 4.4 切语言保护

**Why:** 用户已经基于"翻译成英语"改了 prompt,这时切到日语,
立刻把 prompt 覆盖回"翻译成日语"的默认模板会很粗暴 — 用户的手改被静默吞掉。

**方案:** `promptIsCustomized` 判断当前 prompt 与 default 是否一致,
不一致(targetLang watch)就**不**覆盖,让用户决定是否要重置。

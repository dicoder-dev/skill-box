**日期:** 2026-07-08
**状态:** 进行中

## 1. 需求

用户原话:

> 优化首页导入技能的排序顺序:
> 1. 可导入的技能优先排在前面;
> 2. 已经导入或不可导入的技能排在后面。

解构需求:

1. **入口位置**:首页 `SkillsView` 顶部"导入技能"按钮(`@click="goOnboarding"`)
   → `OnboardingImportDialog` 弹窗 → 内嵌 `OnboardingView` 的 phase2 选择列表
   (`v-for="tab in toolTabs"` 下的 `<li v-for="f in foundByTool[activeToolId].items.filter(...)">`)
2. **"可导入"的定义** = `!isDisabled(f)`,即 `category !== 'system'` ∧ `existingNames.value` 不含此 skill name(客户端 store 已不存在同名)∧ 跨工具同名未被另一个 tool_id 勾上。
3. **期望**:在 phase2 列表里,所有可勾选的项排到前面;已存在(`tagExists` 灰色标签)和 system(`disabledSystem` 灰色标签)的项排到后面。
4. **不动**:`isDisabled` / `disabledReason` / `selectExclusiveByName` 这些判定逻辑。只在 `foundByTool` computed 里**改排序顺序**,把"可勾选的 rank=0,已存在 rank=1,system rank=2"。

## 4. 问题与方案

**为何不把排序移后端 / 不要新增 "imported" 字段:**
- 后端 `onboarding/scan` 返的 `onboardingFoundLite`(post_onboarding_scan.a.go:30-38)目前只有 tool_id / name / version / source_path / category,**没有"已存在"标记**。
- 前端 `existingNames`(`loadExistingNames()`,line 85-99)已经拉了一次 `listSkills` 拿到全量 store skill name,所以前端完全有能力判定。
- 改前端 computed 排序**零请求增量**,不动 schema 不动接口。

**为何不动 `isDisabled` / `selectExclusiveByName` / `disabledReason`:**
- 这些是 UI 状态的判定,跟排序是两个维度。
- `isDisabled` 仍然保留作为"是否可勾选"的真相源;"已存在"在该视图里**既排序靠后,又置灰**,视觉一致。

**为何不在 `OnboardingImportDialog.vue` 加排序(避免双处实现):**
- dialog 只是 wrapper,真的列表是 OnboardingView 的 phase2。改 View 一处即可,dialog 自动受益。

**rank 顺序选择:**
- 用户原话:"可导入优先排在前面;已经导入或不可导入的排在后面"
- "已经导入的" / "不可导入的"并列靠后 — 两者内部顺序按 `category`(user 已被导入 vs system),保持现有视觉:user 整体比 system 更"显眼"。所以最终:**可勾选 → 已存在(user) → system**。
